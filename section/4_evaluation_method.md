# 評価手法
評価に用いたデータは、3章で挙げた3種類のモデルについて、STRIDE、STRIDE+AI及びMAESTROの手法を用いて脅威モデリングを行った結果を用いました。データの収集においては、3名1チームの構成で計3チームにおいて、各チームで3種類のモデルに対してSTRIDE、STRIDE+AI及びMAESTROの手法を用いて評価を行い、その結果を収集しました。また、データ収集の際の各手法の実施方法については、下記の通りです。

## STRIDE
STRIDEについては、用意されたDFD図に対して下記の流れで実施しました。

1. 信頼境界の設定(3つ)

3. リスクの評価と脅威に対する対策の提示

5. リスク評価と緩和策の計画  
[5]のリスク評価手法を参考に、リスク測定基準とマトリックスを用いて、各脅威の「発生可能性」と「影響度」を評価します。その結果に基づき、対処すべき脅威の優先順位を決定します。リスクは以下の式および値に基づき計算します。

R = P × I

- P (Likelihood / 可能性): 運用条件または敵対的な条件下で、その脅威が発生する確率の推定値。
- I (Impact / 影響): 脅威が達成された場合に発生する可能性のある結果の深刻度レベル。

| High (高) | 3 |

## PHANTOM-B
PHANTOM-Bについては、用意されたDFD図に対して下記の流れで実施しました。

1. 適用範囲の特定  
DFD図上で、次に当たる要素を破線で囲み、PHANTOM-Bの適用範囲とします。DFDの記法は拡張しません。
    - LLM／AIモデルそのもの、またはそれを呼び出す外部エンティティ(3rd Party LLM API等)
    - LLMの出力をそのまま扱うプロセス(要約、推薦、エージェント)
    - LLMへの入力を組み立てるプロセス(文字起こし結果の受け渡し等)

エージェント型のシステムでは、エージェント間の受け渡しも範囲に含めます。エージェント間の指示・応答はLLMの出力が別のLLMの入力になる経路であるため、範囲は分割せず1つの破線で囲みます。

なお、FactoryQualityAppはLLMを持たないため、各問いの「LLM」を「AIコンポーネント(画像認識モデル)」に読み替えて適用します。

1. 9つの問いの適用  
範囲内のLLM／チャットボットのコンポーネントごとに、2章で示した9つの問いを投げて、問題がどのように現れうるかを検討します。PHANTOM-Bは分類のカテゴリではなく問いかけとして用い、一般的な脅威から対象システムに固有の具体的な脅威へと落とし込みます。
検討結果は、対象コンポーネントごとに下記の形式で記録します。

| | 問い | 脅威 |
| ---- | ---- | ---- |
| P | どうすればプロンプトインジェクションが可能か? | |
| H | ハルシネーションが想定を超えたらどうなるか? | |
| A | LLMを擬人化していないか? | |
| N | いつ、誰に対して、出力を説明・正当化する必要があるか? | |
| T | 学習データに偶発的または意図的な品質問題があったらどうなるか? | |
| O | LLMはどのような判断を行い、何に対してどのような制御権を持っているか。それにより意図せず攻撃面が拡大していないか?(「エージェント型AI」のデプロイパターンでは特に重要) | |
| M | 脅威モデリングを含め、SDL(セキュア開発ライフサイクル)のその他のセキュリティエンジニアリングを適切に実施したか? | |
| - | LLMがアクセスできるデータ、および情報が開示され得る先を制御できているか? | |
| B | LLMにはどのようなバイアスがあり、それはこのユースケースにおいて許容できるか? | |


1. 網羅性の確認  
問いのすべてについて、見つけた脅威が1件以上あるかを確認します。無い場合は「見つけた脅威」列に「該当なし」とその理由を記載します。見つけた脅威がどの文字にも当てはまらない場合もあり、その場合は無理に当てはめずに記録します。
